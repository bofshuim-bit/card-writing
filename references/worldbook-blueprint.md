# 世界书：蓝图与真值

## 一、两个真值（先记这个）

| 类型 | 字段 | 效果 |
|---|---|---|
| **蓝灯（常驻）** | `"constant": true`，`"key": "[]"` | 每轮都注入，不看关键词 |
| **绿灯（关键词触发）** | `"constant": false`，`"key": "[\"关键词\"]"` | 只有关键词出现在上下文里才注入 |

> 常见误区：以为 `role: 1` 是蓝灯。不是。平台认的是 `constant`。写错的话全部变成绿灯，
> 界面里的"固定传输字符数"会小得可怜（比如只有 1500），因为你没有常驻条目。

## 二、字数预算（硬限）

```
人设字数 + 所有蓝灯字数 ≤ 15000 字符
```
超限后果分两级：
- **总预算超**（人设 + 全部世界书）：按优先级裁掉排后面的条目，卡还能用但设定会缺。
- **固定传输超**（人设 + 蓝灯 > 15000）：**过不了审核**，卡发不出去。

所以蓝灯要克制，绿灯可以多。

参考分配：
- 人设 1500~3000
- 蓝灯 4000~7000（4~6 条）
- 绿灯 3000~5000（20~35 条，不算进固定传输）

## 三、绿灯为什么触发不了（高频 bug）

绿灯的关键词必须**先出现在对话里**才会被检索。

```
蓝灯没提到「金辉超市」→ AI 不知道有这个地点 → 正文不会写 → 绿灯永远不触发
```

**解法：蓝灯里放一份名录**，把绿灯的关键词点名：

```
本卡会出现的地点与人：学校、教室、走廊、操场、金辉超市、散步的路、穗穗老家、医院。
物件：手链、信、礼盒、眼镜、香辣无骨鸡爪、杨枝甘露。
```

这样 AI 知道它们存在，自然会写到，绿灯才被点亮。

## 四、蓝灯写什么（4~6 条，每条 600~2000 字）

| 条目 | 写什么 |
|---|---|
| **剧情主脉络** | 完整时间线（只给 AI，不提前剧透）+ 场景级细节 + 硬规则 + **绿灯名录** |
| **人物档案** | 外貌/性格/说话方式（带 3~6 条示例台词）/小动作/喜好/恐惧/关系史 |
| **世界与基调** | 时代、地点、学校/单位作息、日常细节、氛围、基调 |
| **玩家** | {{user}} 是谁、性格底色、知道什么 |
| **写作规范** | 视角、长度、语言、禁止、每轮怎么写、伏笔处理、节奏 |
| **状态栏协议** | 每轮必出的 16~20 个键 + 要点（也可以只放人设里） |

**剧情主脉络要写"具体发生什么"**，不要写"两人逐渐熟悉"这种概括：

✅
```
放学「我」去找她套近乎，本以为不好说话，结果意外地好说话。
她收拾东西很慢，把笔一支支放进笔袋。
```
❌
```
两人在相处中感情逐渐升温。
```

## 五、绿灯写什么（20~35 条，每条 120~400 字）

结构：**场景 + 具体细节 + 怎么写**

| 类别 | 示例 |
|---|---|
| 地点 | 学校、家里的巷子、超市、便利店、操场、老居民楼 |
| 物件 | 手链、信、礼盒、眼镜、校服、毕业照 |
| 人物 | 父亲、她的父亲、同学、老师、奶奶 |
| 场景 | 雨天、晚自习、走廊、第一次主动说话、最后一条消息 |
| 机制 | 阶段时间线、网恋那三个月、考试周 |

示例（学校）：

```
教学楼四层，高二（3）班在三楼东头。早读 7:20 站着背英语，声音一片；
第一节课 8:00，上课铃是老式电铃，震得人一激灵。晚自习安静得能听见翻卷子的声音。
走廊很长，课间全是人；靠窗一排能看见操场。教室课桌是旧的，桌面有刻字和圆珠笔印。
窗户关不严，冬天有缝往里灌风。走廊尽头有饮水机，热水总不够。
```

细节要能直接写进正文（电铃、圆珠笔印、热水的温度），不要写"很有青春气息"。

## 六、关键词怎么写

- 一条绿灯放 3~6 个关键词，**用读者/AI 真实会说的词**
- 别放太通用的词（"我""今天"），会误触发
- 同义词一起放：`["超市","金辉超市","鸡爪"]`
- 人名放全名 + 称呼：`["穗穗","她"]`（"她"太通用，不建议）

## 七、JSON 结构

```json
{
  "entries": {
    "0": {
      "uid": 1,
      "comment": "剧情主脉络",
      "content": "……",
      "key": "[]",
      "keysecondary": "[]",
      "constant": true,
      "disable": false,
      "depth": 4,
      "order": 0,
      "position": 1,
      "probability": "100.00",
      "role": 0
    }
  }
}
```

注意：
- `probability` 必须是**两位小数字符串** `"100.00"`，写 `100` 会报错
- `role`、`depth` 必须是整数
- `key` 是**字符串形式的 JSON 数组**，不是数组本身

## 八、检查清单

- [ ] 蓝灯 `constant: true` 且 `key: "[]"`
- [ ] 绿灯 `constant: false` 且关键词具体
- [ ] 蓝灯里有绿灯关键词名录
- [ ] 人设 + 蓝灯 ≤ 15000
- [ ] 每条蓝灯 600 字以上，不是一两句
- [ ] 绿灯每条 120 字以上，有具体细节
- [ ] probability 是 "100.00" 字符串

## 九、层级、卡型与 position

世界书条目按**层级**组织，导出顺序由层级决定。四层足够覆盖绝大多数卡：

| 层级 | 放什么 | position | 灯色 |
|---|---|---|---|
| 世界设定层 | 世界观总纲、历史、地图 | 0（角色卡之上） | 蓝 |
| 角色层 | 角色速览、角色设定、性格 | 1（角色卡之下） | 单角色卡全蓝；多角色卡速览蓝、详情绿 |
| 场景物品事件层 | 物品、能力、场景、事件、NPC | 1 | 绿 |
| 文风约束层 | 文风指导、禁忌 | 2（作者注之上） | 蓝 |

**按卡型定蓝绿**：
- **单角色卡**（1 个核心角色，拆成多条也算单角色）：该角色所有条目蓝灯常驻。
- **多角色卡**（≥2 核心角色）：**角色速览一条蓝灯**（列名字+一句话），每个角色的详情绿灯（keys = 全名、昵称、外号）。

这条是实战结论：多角色卡如果每个角色都常驻，蓝灯预算立刻爆 15000；如果全绿灯，AI 又不知道有这些人。速览蓝 + 详情绿是唯一稳的解法。

## 十、平台差异（写之前先确认）

| | 本地酒馆 | MMD 当前版 | MMD 新页沙盒 |
|---|---|---|---|
| 条目标题上限 | 无 | **20 字（超限 ERROR）** | **20 字（WARN）** |
| 世界书交付 | 可合并 | 可合并 | **必须独立 JSON**，根对象只留 `entries` |
| 导入位置 | 独立 | 独立 | 不能并进 6 键正则 JSON（顶层出现 `entries` 会被判 ERROR） |
| 固定传输预算 | — | 15000（保守） | 15000 未确证，按 15000 保守做 |

**条目标题 20 字**最容易踩：`剧情主脉络`（5 字）没问题，`多角色关系网与势力分布总表`（13 字）也还行，但写成一句话就会超。

## 十一、世界书工作流（条目多时）

条目超过 20 条，建议目录化维护，别在一个 JSON 里手改：

```
工作/世界书/
├─ entries/      一条一文件（正式）
├─ drafts/       未确认草稿
├─ index.md      导航（只读，不手改结构）
└─ notes.md      设计决策记录
```

- 结构操作（增删改移）走脚本，不要手改 uid/order
- 导出 JSON 是产物，**不要拿导出的 JSON 当编辑源**——下次一改就丢

条目少（<20）时可以直改 JSON，但改完必须重跑校验。
